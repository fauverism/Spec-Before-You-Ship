Lesson 11 — Final

Archive & Compound

Close the change, merge the specs, and see what the second feature looks like when the AI already knows everything about the first.

Everything you built across eleven lessons is about to become permanent context. When you run /opsx:archive, the change folder closes, the delta specs merge into the main library, and Bridgespec's decisions become part of the codebase's institutional memory. Every future AI session in this repo starts from that.

That's the compound. The first change takes the most effort. Every change after inherits what came before.

Run the Archive

One command. No pre-flight required — the archive command runs its own validation gates.

$ openspec archive bridgespec-scaffold

✓ delta specs valid (3 specs)

Done. openspec/specs/ updated. Workspace is clean.

The operation counts tell you what happened to the spec library: eight requirements added across three spec files, one requirement modified (the isMissing correction from lesson 10). Everything validated before a single file was written. Atomic — if any validation had failed, nothing would have changed.

The change folder didn't disappear — it moved to archive/ with a date prefix. Every decision you made is still there, permanently, with a timestamp. The openspec/specs/ directory went from empty to populated with three fully-formed spec files. That's the spec library.

The Second Change — Where Compounding Starts

In lesson 10 you deferred JSON export to a new change. Start it now and watch what happens:

/opsx:new add-json-export

✓ Created openspec/changes/add-json-export/
✓ Wrote .openspec.yaml

  Ready to create the first artifact?

Now run /opsx:ff and open the generated proposal.md. Look specifically at the out-of-scope list and the definition of done. Compare it to what the same command would have produced in lesson 3, before the spec library existed.

What the AI knows for add-json-export
Before writing a word, the AI reads:
openspec/specs/export/spec.md — specToMarkdown() is already defined, tested, and ships the ⚠ MISSING IN FIGMA flag. Any new export format must match that behavior contract or explicitly diverge from it.
openspec/specs/contract-editor/spec.md — SpecObject's shape, what fields exist, what types they carry. The AI won't invent a new data structure for JSON export.
openspec/changes/archive/2026-03-27-bridgespec-scaffold/design.md — specToMarkdown() is a pure function in src/lib/export.ts. The JSON equivalent goes in the same file, same pattern.
openspec/changes/archive/.../design.md (Deferred) — "Multiple export formats (v2): YAML, JSON, custom templates." This change is the planned v2. The AI knows it was anticipated, not improvised.

The proposal the AI generates for add-json-export will reference specToJson() by name, place it in src/lib/export.ts alongside specToMarkdown(), and note that the format must include the isMissing flag in the same way the markdown output does. None of that required you to explain anything. It was already in the library.

That's the compound. The first change pays for everything. Every change after is cheaper because the previous ones did the thinking.

The workspace is exactly as clean as when you started in lesson 3, except now there are three spec files, seventeen passing tests, a deployed app, and a permanent record of every decision that produced them.

What you've actually built

Bridgespec is the app. That was always secondary. What you actually built is a habit: write the proposal before the code, write the scenarios before the design, write the design before the tasks, let the AI implement against everything you've decided, fix the artifacts when reality disagrees with them, archive when it's done.

That habit compounds. The tenth change in this repo will take half the time the first one did — not because the AI got smarter, but because the spec library got bigger and the decisions got cheaper to make.

Lesson 04

The Proposal

The first artifact you write. Not a PRD, not a brief, not a ticket. Two pages that answer three questions: what's broken, what you're building, and what you're not.

A proposal.md has one job: align you and your AI on what you're building before either of you touches code. It doesn't need to be comprehensive. It needs to be honest — honest about the problem, honest about the scope, honest about what's out of bounds.

Most people write proposals that are too long, too optimistic, and missing the most important section. This lesson shows you what each section does, shows the failure mode for each, and then gives you the Bridgespec proposal to write.

The Four Sections

Problem

The pain. Not "users want X" — why does the absence of X cause a specific kind of failure. One to three sentences. Resist the urge to describe the solution here.

The test: if someone read only this section, would they understand what's broken — without needing to know what you're building to fix it?

config rule → state the problem before the solution
What we're
building

The shape of the solution in plain English. No implementation details yet — that's design.md. Two to four sentences describing what the thing does, who uses it, and what it produces.

The test: could a designer, a developer, and a PM read this and all picture the same thing?

What we're
not building

The hardest section to write and the most valuable one to have. Explicit out-of-scope items prevent scope creep from the AI. If it's not in this list, the AI will reasonably assume it's in scope when it seems useful.

The test: for every item on this list — did you consider it and deliberately decide against it, or did you just not think of it? Both belong here, but one is more important.

config rule → include explicit out-of-scope items
Definition
of done

One sentence. What does a person do, what do they get, and is there anything else they need to understand what they got? Write it like a test assertion — a condition that is either true or false.

The test: could you, right now, sit down and verify whether this sentence is true or false for a given build? If the answer requires judgment, the sentence is too vague.

config rule → define done in one sentence

The Failure Mode

Here's what a bad proposal looks like. You've seen versions of this — you may have written versions of this. Study it before you write yours.

proposal.md — bad version don't write this 
# Proposal: Bridgespec

## Overview
Bridgespec is a tool to help UX engineers document components.
It will improve the design-to-engineering handoff process by
providing a structured way to capture component information.

## Features
- Component name and description
- State documentation
- Token management
- Export functionality
- Maybe Figma integration
- User accounts for team sharing

## Goals
Make the handoff process better and reduce friction between
design and engineering teams.

Four problems with that proposal. First, there's no problem statement — it describes the solution without explaining what's broken. The AI doesn't know whether this is a pain-driven build or a nice-to-have. Second, "maybe Figma integration" and "user accounts" are undecided scope items — the AI will now include them in the design because you didn't explicitly exclude them. Third, the goals are unmeasurable; "make the handoff process better" cannot be verified. Fourth, there's no definition of done — the AI has no exit condition.

The AI that reads this will produce artifacts that could mean anything. It will ask clarifying questions on every message. You'll spend more time re-explaining intent than the proposal would have taken to write properly.

The Bridgespec Proposal

Create this file now. Type it — don't paste it. The act of typing it is the thinking.

openspec/changes/bridgespec-scaffold/proposal.md write this 
# Proposal: Bridgespec Scaffold

## Problem

UX engineers sit between design and engineering but have no
dedicated format for documenting the gap between them. Figma
captures visual intent but cannot express async states, error
states, or the reasoning behind design decisions. Code captures
behavior but not intent. The result: loading states get skipped,
error states get invented at deadline, and the "why" behind a
design decision is lost by the time someone has to change it.

## What we're building

A single-page React app where a UX engineer defines one component
contract at a time: its states (including those missing from Figma),
its design token values by name and resolved hex, its purpose in
plain English, and its edge cases with exact measurements. The app
exports a .spec.md file that lives in the repo alongside the
component and travels with it through design review and code review.

## What we're not building

- Figma plugin or API integration (v2)
- User accounts, auth, or cloud storage (v2)
- Real-time collaboration or multi-user editing (v2)
- Component library browser or multi-file management (v2)
- Design token syncing from a token source of truth (v2)
- Storybook integration (v2)
- Any backend of any kind (deliberately out of scope)

## Definition of done

A UX engineer can open the app, define a Button component with all
its states including gap-detected missing ones, assign token values,
add edge cases, click Export, and receive a Button.spec.md file
they can drop into a repo and show to a designer and a developer
without additional explanation.

The definition of done is one sentence — a long sentence, but one. Read it aloud. You can picture someone doing exactly that sequence of actions. You can picture the file they receive. You know when it's done.

The Out-of-Scope List Protects You

Without "any backend of any kind," the AI might reasonably suggest localStorage for persistence. It's a frontend-only feature, it's useful, it's not unreasonable. But it's not what you're building in this iteration, and adding it would add complexity to lessons 6 and 7 without adding value to the tutorial.

Every item with "(v2)" is a decision you've made — not an omission. The AI now knows it can reference those features as future work but cannot include them in the design. That's the difference between this out-of-scope list and not having one: the AI's design doc will be scoped correctly from the first draft instead of after two rounds of correction.

Before you move to specs

Ask the companion to review your proposal. Not to rewrite it — to evaluate it. Tell it you're on lesson 4 and paste the file. It will check the problem statement, the out-of-scope list, and the definition of done against the rubric. If the companion says your definition of done requires judgment to verify, it's right. Fix it before moving on. A weak proposal produces weak specs, which produce a weak design, which produces a task list that doesn't match what you actually want to build.

Unlock the Next Artifact

Save the file. Then check status:

$ openspec status --change bridgespec-scaffold

Progress: 1/4 artifacts complete

[x] proposal    done
[ ] specs       ready to write
[ ] design      blocked — needs specs
[ ] tasks       blocked — needs design

One artifact done. Specs unlocked. The AI can now read your proposal before helping with anything else in this change — and it will, every time, automatically.

If you're tempted to keep the proposal short

The problem section in particular wants to be one vague sentence. Resist it. The problem section is the one part of the proposal that the AI cannot infer from context — it doesn't know what's broken in your world, only what you tell it. Three honest sentences about the actual pain produce better specs than three paragraphs about the solution.

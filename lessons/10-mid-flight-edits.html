Lesson 10

Mid-flight Edits

Implementation reveals things planning can't. When the spec turns out to be wrong, when scope needs to shrink, and when someone wants to add something — three situations, three different responses.

Lesson 9 covered what to do when the AI produces something that doesn't match your spec. That's deviation — the spec is right, the implementation is wrong, fix and resume.

This lesson is different. Sometimes during implementation you discover that the spec itself is wrong — not because the AI misread it, but because writing the code revealed an assumption that doesn't hold. Or someone asks to add a feature mid-flight. Or a task turns out to be bigger than expected and v1 needs to shrink.

These are genuine requirement changes, and they each have a specific response. The wrong response to all three is to keep implementing against a spec you know is wrong and fix it later. That way lies a codebase that disagrees with its documentation — which is worse than no documentation at all.

The Three Situations

correction The spec has a mistake
"While implementing StateList, I realized the spec says clicking a missing state should set isMissing to false — but that's wrong. The user needs to add a description first. isMissing should only clear when the description field is non-empty."
The spec was wrong. Stop, correct the spec, uncheck the affected task, resume. The correction is a deliberate change to behavior — it deserves a record in the artifact, not a patch in the code.
reduction Something is too complex for v1
"Task 3.5 — TokenList with the drift warning indicator — is turning into a much bigger component than the task estimate suggests. The hasDrift logic requires a source-of-truth comparison that's out of scope per the design doc. Cut it from v1."
The scope needs to shrink. Update the proposal's out-of-scope list, update the design doc's deferred section, simplify the task, resume. Do not silently skip the feature — document that the decision was made and why.
expansion Someone wants to add something
"While demoing the preview pane, a colleague suggests also adding a copy-as-JSON export. It would only take one more function."
This is scope creep, regardless of size. Do not add it to this change. Write it down — in the open questions section of design.md, or in a note — and create a new change for it after this one archives. Protecting the boundary of a change is what makes the archive meaningful.

Handling a Correction — In Detail

Here's the full sequence for the isMissing correction above. The principle is the same as lesson 9's deviation response: fix the artifact before touching the code. The difference is that you're correcting a spec you wrote intentionally, not a misinterpretation by the AI.

1
Stop implementation
Do not implement the wrong behavior and plan to fix it later. The wrong behavior is in the tasks.md — the AI will implement it exactly as written.
2
Edit the spec
Open specs/contract-editor/spec.md. Find the scenario that described the old behavior. Replace it with the corrected scenario — specifically: isMissing clears only when description is non-empty.
3
Uncheck the affected task
If task 3.4 was already checked, mark it [ ] again. The implementation based on the old spec needs to be redone. If it wasn't checked yet, no change needed — the AI will read the corrected spec when it gets there.
4
Validate the updated spec
Run openspec validate --change bridgespec-scaffold to confirm the edited spec file still passes. A typo in a scenario header can silently break the validator.
openspec validate --change bridgespec-scaffold
5
Resume in a fresh context
Clear the context window. Run /opsx:apply. The AI reads the corrected spec and implements against it. The unchecked task will be picked up automatically.

The corrected scenario in the spec looks like this:

specs/contract-editor/spec.md — corrected scenario 
#### Scenario: user documents a previously-flagged state

  was:
  - GIVEN the states array contains an 'error' entry with isMissing: true
  - WHEN the user adds a description to the error state
  - THEN isMissing is set to false on that entry

- GIVEN the states array contains an 'error' entry with isMissing: true
- WHEN the user types a non-empty description for the error state
- THEN isMissing is set to false on that entry
- AND if the user clears the description field, isMissing returns to true

One scenario becomes two behaviors — the happy path and the round-trip. Both needed to be specified. The correction surfaced that.

Handling a Reduction — In Detail

The hasDrift indicator turns out to require more work than estimated. The design doc already noted that drift detection without an automated source of truth is of limited value. The right move is to make that deferred status explicit in the artifact, not leave it as a broken or incomplete task.

design.md — updated deferred section 
## Deferred

- Token drift detection (v2): comparing resolvedValue against a
  design token source of truth requires a config file or API.
  Out of scope; hasDrift is manually flagged by the user in v1.
  Removed from v1 entirely during implementation — the manual-flag
  UX adds complexity without value when there's no automated source
  of truth to compare against. hasDrift field stays in SpecObject
  for v2 compatibility but is not surfaced in the editor or export.

Then simplify task 3.5 to remove the warning indicator work:

tasks.md — updated task 3.5 
- [ ] 3.5 Create src/components/TokenList.tsx — renders SpecToken[].
      Two inputs per row: name and resolvedValue.
      Yellow warning indicator when name is set but resolvedValue is empty.
      No drift indicator in v1 — see design.md Deferred.
      Dispatches UPDATE_TOKEN. 30 min.

The change is documented in two places: the design doc records the decision and the reason, the task reflects the reduced scope. When a colleague reads the archive six months from now, they'll see exactly when and why the drift indicator was cut — not just that it's missing.

Handling an Expansion — The Hard Line

The copy-as-JSON request is reasonable. It probably is one function. Say no anyway.

The reason is not about effort — it's about what the archive means. When this change archives, its proposal.md becomes a permanent record of what was decided and why. If you add JSON export mid-flight, that decision has no proposal, no spec, no design rationale. It just appears in the code. The next person to touch that function has no context for it. The archive loses its integrity.

The right response:

design.md — open questions, updated 
## Open Questions

...

- JSON export format: a colleague noted this would only require one
  additional specToJson() function alongside specToMarkdown().
  Deferred to a dedicated change so the format decision can be
  properly specced. See next change: add-json-export.

Record it. Defer it. The next change starts from a note, not from nothing. That's the compound effect of spec-driven development — not just that this change is documented, but that the decision to defer is documented, which makes the next change faster to plan.

/opsx:sync — Checkpoint Before You're Done

If you made significant spec corrections mid-flight, you can push the updated delta specs to the main spec library without closing the change. This is useful when you're working across multiple sessions and want the corrections reflected in openspec/specs/ before you archive.

$ openspec validate --change bridgespec-scaffold
✓ 3 specs valid, 0 errors

$ openspec sync --change bridgespec-scaffold
Syncing delta specs...
+ gap-detection/spec.md      2 requirements applied
+ contract-editor/spec.md    3 requirements applied (1 modified)
+ export/spec.md             3 requirements applied

openspec/specs/ updated. Change bridgespec-scaffold still active.

The change directory is untouched. The main spec library is updated. You can sync as many times as you like during implementation — unlike archive, which is one-time and final.

The invariant worth protecting

The right question to ask about any mid-flight change is: will the archive of this change accurately reflect the decisions made? A correction that's recorded in the spec: yes. A reduction that's documented in design.md: yes. An expansion that bypassed planning: no. That last one doesn't just hurt this change — it degrades every future change that builds on this code, because the context for that function simply won't be there.

The inconvenience of creating a new change for an expansion is the price of keeping the archive honest. It's a small price, and it compounds in your favor every time someone reads the archive six months from now and understands exactly what was built and why.

End of lesson 10
  • You can distinguish the three mid-flight situations: correction, reduction, expansion
  • Corrections go into the spec first — always fix the artifact before fixing the code
  • Reductions are documented in design.md's Deferred section, reflected in the task list
  • Expansions are deferred to a new change — protecting the current change boundary is what keeps the archive honest
  • You know /opsx:sync for mid-flight checkpoints and exactly how it differs from /opsx:archive

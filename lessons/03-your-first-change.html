Lesson 03

Your First Change

Run one command, watch a folder appear, and understand exactly what OpenSpec created — and what it deliberately didn't.

OpenSpec tracks work in changes. A change is an isolated folder — one per feature, one per refactor, one per meaningful unit of work. Everything that belongs to Bridgespec's initial build lives in one change folder. When it's done, it archives and the workspace is clean again.

Run this in your AI tool's chat panel now:

/opsx:new bridgespec-scaffold

The AI runs the command and reports back:

✓ Created openspec/changes/bridgespec-scaffold/
✓ Wrote .openspec.yaml

  Artifact status:

  ● ready     proposal.md
  ○ blocked   specs/             needs: proposal
  ○ blocked   design.md          needs: specs
  ○ blocked   tasks.md           needs: design

  Change created. Ready to create the first artifact?
  Use /opsx:continue for step-by-step, /opsx:ff to
  create all planning artifacts at once, or describe
  what you want to build.

That's it. No artifact files yet. Just the folder and the metadata file — the scaffold.

What Was Created

openspec/changes/bridgespec-scaffold/
└── .openspec.yaml       ← the only file /opsx:new writes

Open .openspec.yaml. It contains two things:

openspec/changes/bridgespec-scaffold/.openspec.yaml yaml 
schema: spec-driven
created: 2026-03-27T...

schema: spec-driven tells OpenSpec which artifact graph to use for this change — the one that produces proposal, specs, design, and tasks in that order. created is the timestamp that becomes the archive folder name when this change is done.

Everything else — the four artifact files — is deliberately absent. You haven't written any of them yet. That's the design. The scaffold waits for you.

The Artifact Graph

The status output you saw is the artifact graph for the spec-driven schema. It encodes a dependency order that isn't arbitrary:

artifact dependency graph — spec-driven schema
ready proposal.md no dependencies — start here
└──►
blocked specs/ needs a proposal to specify against
└──►
blocked design.md needs scenarios to design toward
└──►
blocked tasks.md needs a design to break into tasks

The order matters. You can't write meaningful scenarios without a proposal — you don't know what you're specifying. You can't make real design decisions without scenarios — you don't know what cases to handle. You can't write a task list without a design — you don't know what to build. The graph enforces the thinking order that produces useful artifacts instead of vague ones.

Say No to Fast-Forward

The AI just offered you three paths: /opsx:continue, /opsx:ff, or manual. In production, fast-forward is the right choice most of the time — it generates all four artifacts in one pass and you review them. In this tutorial, it's the wrong choice.

AI offering
Use /opsx:continue for step-by-step, /opsx:ff to create all planning artifacts at once, or describe what you want to build.
skip
/opsx:ff Generates all four artifacts immediately. You'll review output you don't yet understand how to evaluate. Save this for lesson 8.
skip
/opsx:continue AI writes the proposal for you. Useful later — but writing your first proposal by hand is how you learn what makes one good.
do this
Write proposal.md yourself, in your editor, right now. You already know what to write — the proposal for Bridgespec has been sitting in the OpenSpec artifacts tab since lesson 1.

Tell the AI you'll write the proposal manually and you'll let it know when it's ready:

I'm going to write proposal.md by hand. I'll come back
when it's done.
Understood. I'll be here when you're ready to move to specs.

Check the Status Anytime

While you're working, you can always see where you are. Run this in your terminal — not in the AI chat:

$ openspec status --change bridgespec-scaffold

Change: bridgespec-scaffold
Schema: spec-driven
Progress: 0/4 artifacts complete

[ ] proposal    ready to write
[ ] specs       blocked — needs proposal
[ ] design      blocked — needs specs
[ ] tasks       blocked — needs design

After you write the proposal in the next lesson, it'll look like this:

Progress: 1/4 artifacts complete

[x] proposal    done
[ ] specs       ready to write
[ ] design      blocked — needs specs
[ ] tasks       blocked — needs design

One artifact done, one unlocked. The graph advances every time you write a file. By lesson 7, all four boxes are checked and /opsx:apply becomes available.

What the AI reads before any artifact

When the AI helps you with any artifact in this change, it reads three things first: your openspec/config.yaml (the stack context you wrote in lesson 2), the .openspec.yaml in this change folder (the schema), and any artifacts already completed in the change. By lesson 4 that's the proposal. By lesson 6 it's the proposal and the specs. The context accumulates with every artifact you write — the AI gets more accurate, not less, as the change progresses.

If the command wasn't found

If your AI tool says it doesn't recognise /opsx:new, two things to check: first, confirm you ran openspec config profile and selected expanded in lesson 2. Second, restart your IDE — slash commands installed by openspec init are loaded at startup, not hot-reloaded. One restart is all it takes.

What You Have

openspec/changes/bridgespec-scaffold/
└── .openspec.yaml         ← schema: spec-driven, timestamp

waiting to be written:
    proposal.md            ← lesson 4
    specs/                 ← lesson 5
    design.md              ← lesson 6
    tasks.md               ← lesson 7
End of lesson 3
  • You understand that a change is an isolated folder — one per unit of work
  • You know that /opsx:new scaffolds only — it writes no artifact content
  • You understand the artifact dependency graph and why the order is enforced
  • You've chosen to write artifacts manually, and understand why that's the right call here
  • You can check progress anytime with openspec status

Lesson 06

The Design Doc

Architecture before implementation. The one artifact where the AI drafts and you review — and where the hardest question is always "what did you consider and reject?"

The design doc is where architecture gets decided. Not described after the fact — decided before a line of implementation code runs. It answers three questions the specs deliberately left open: how will the data flow, what are the component and function boundaries, and what did you choose not to do and why?

The proposal told you what's broken and what you're building. The specs told you exactly what correct behavior looks like. The design doc tells you — and your AI — how to build it. An AI that implements without a design doc will make those decisions implicitly, differently every time, and often in ways that create rework three lessons from now.

This is also the first lesson where you run /opsx:continue and let the AI draft an artifact. Lessons 4 and 5 were manual because you needed to build the muscle memory. This one you review critically. The pattern from here forward: AI drafts, you own the decisions.

What the Design Doc Is Not

Before the sections: three things a design doc is commonly mistaken for, and why each one is wrong.

It's not a spec. Specs describe what the system must do. The design doc describes how the implementation will achieve that. "The export function SHALL never throw" is a spec. "specToMarkdown will be a pure function that takes a SpecObject and returns a string, with no side effects" is design.

It's not a task list. A task list is a sequence of atomic actions. A design doc is a set of decisions and their rationale. The task list emerges from the design doc — you can't write meaningful tasks until you've made architectural decisions. That's exactly why design.md comes before tasks.md in the artifact graph.

It's not a README. A README describes what the code does for someone using it. A design doc records why the code is shaped the way it is, for someone modifying it. The design doc's reader is future-you, six months from now, wondering why the state lives in useReducer instead of Zustand.

The Sections

Context

Two to four sentences. Sets up the problem space for anyone reading this cold. Write it for a competent developer who hasn't read the proposal. What's being built, why it exists, what constraints are already fixed.

Goals &
Non-Goals

The design's scope boundaries. Goals are the outcomes this design must achieve. Non-goals are the outcomes it explicitly doesn't need to achieve. Non-goals are just as important as goals — they're your license to keep the design simple.

Decisions

The heart of the document. Each entry names a decision, states what was chosen, and — this is the part AI commonly skips — records the alternative that was rejected and the specific reason it lost. Without the rejected alternative, the decision isn't a decision. It's just a description of what you built.

config rule → name every pure function before implementation
Risks &
Trade-offs

The honest accounting. What could go wrong with the chosen approach? What are you trading away to keep the design simple? Write the risks you actually believe, not the ones that sound impressive in a document.

Deferred

Everything you considered and explicitly left for a later change. This section protects the implementation from scope creep. If it's not in the deferred list and not in non-goals, the AI will treat it as in scope.

config rule → explicitly list what is deferred to a later change
Open
Questions

Decisions you haven't made yet. Not things you don't know — things you've deliberately chosen not to resolve before implementation. Naming them here means they stay visible instead of getting answered implicitly in code.

The Decision Entry Test

Every entry in the Decisions section should survive this test: if you removed the "chosen" line and only read the "rejected alternative" and the "reason," would you arrive at the same choice? If yes, the rationale is strong. If you can't tell, the rationale is vague.

state management — vague entry fails the test 
### State management

Chosen: useReducer at app root

State is managed with useReducer because
it works well for this use case and keeps
the architecture simple.
state management — good entry passes the test 
### State management

Chosen: useReducer at app root

Rejected: Zustand — adds an external
dependency with no benefit at this scope.
SpecObject is flat and the action types
map cleanly to reducer cases. Zustand's
value shows at 5+ stores or async slices,
neither of which applies here.

The vague entry says "works well for this use case" — that's true of every decision in every codebase ever. It gives a future developer nothing to work with. The good entry names the alternative, names the threshold at which that alternative would win, and explains why Bridgespec doesn't cross that threshold. A developer reading it six months from now knows exactly when to reconsider.

Let the AI Draft It

Stop here. Do not immediately run /opsx:continue again. Open design.md and read it with the decision entry test in mind. Specifically, look for three failure modes that AI-generated design docs reliably produce:

Decisions without rejected alternatives. The AI will describe what it chose but often skip what it didn't choose and why. Every entry without a rejected alternative is incomplete. Add it yourself — you know what the alternatives were.

Non-goals that are just restated out-of-scope items. "We won't build a Figma plugin" is not a non-goal. "We won't need a plugin architecture, so all component logic can be colocated in src/lib/" is a non-goal. The distinction matters: one is a constraint copied from the proposal, the other is a design consequence.

A deferred section that's empty or missing. This is almost always absent from the first draft. The AI doesn't know what you've thought about and decided to defer. You do. Write it in.

The Bridgespec Design Doc

After you've reviewed and corrected the AI draft, your design.md should contain decisions like these. Use this as a reference, not a paste target — the AI draft will have gotten some of these right. The ones it missed are the ones worth writing by hand.

openspec/changes/bridgespec-scaffold/design.md 
# Design: Bridgespec Scaffold

## Context

Bridgespec is a static single-page React app with no backend.
A UX engineer defines one component contract per session —
states, tokens, edge cases, purpose — and exports a .spec.md
file. The SpecObject defined in src/types/spec.ts is the
single shared data type across the entire app.

## Goals

- Single component contract per session, exported to markdown
- Gap detection that flags missing standard states per category
- Live preview that updates on every keystroke
- Export produces a file a developer can act on without asking questions

## Non-Goals

- No plugin architecture needed: all logic colocates in src/lib/
- No routing needed: single view, no URL changes
- No persistence layer needed: the .spec.md file is the record
- No async operations: every function is synchronous in v1

## Decisions

### State management

Chosen: useReducer at app root, SpecObject as the sole state shape.
Rejected: Zustand — adds an external dependency with no benefit
at this scope. SpecObject is flat, action types map cleanly to
reducer cases. Zustand earns its place at 5+ stores or async
slices; Bridgespec has neither.

### Gap detection as a pure function

Chosen: detectMissingStates(category, documentedStates) → string[]
lives in src/lib/gap-detection.ts as a pure function.
Rejected: Embedding detection logic inside a React component or
custom hook — would make it untestable in isolation. Gap detection
has complex branching across five category types; it needs unit
tests, not component tests.

### Export as a pure function

Chosen: specToMarkdown(spec: SpecObject) → string lives in
src/lib/export.ts. Download triggered by Blob + anchor click.
Rejected: A template engine (Handlebars, Mustache) — adds a
dependency for a function that's 40 lines of template literals.
The output format is fixed and simple; a library adds complexity
without adding capability.

### Three-pane layout

Chosen: Editor left, preview center, export panel right.
Rejected: Tabbed interface (edit / preview / export tabs) —
hides the preview behind an action, breaking the live-update
requirement. The three-pane layout keeps the feedback loop
immediate: type a state, see it appear in the spec instantly.

### No localStorage in v1

Chosen: Session state only. Nothing persists on page refresh.
Rejected: localStorage for draft persistence — the .spec.md file
is the persistence layer by design. Adding localStorage creates
a second source of truth, a sync problem, and a clear/reset UX
question. All three are out of scope for v1.

## Risks and Trade-offs

- The standard state taxonomy (STANDARD_STATES per category) is
  opinionated. Teams with non-standard component systems will need
  to customize it. v1 ships the taxonomy as a constant; v2 should
  make it configurable per project.
- No persistence means accidental tab close loses all work. This
  is the correct trade-off for v1 but will be the first complaint
  from real users.
- specToMarkdown output format is fixed. If teams want a different
  format (YAML, JSON, custom markdown), v1 can't accommodate them.
  This is acceptable; a single format ships faster and teaches the
  pattern.

## Deferred

- Token drift detection (v2): comparing resolvedValue against a
  design token source of truth requires a config file or API. Out
  of scope; hasDrift is manually flagged by the user in v1.
- Multiple export formats (v2): YAML, JSON, custom templates.
- Figma plugin (v2): reads component names and states from Figma
  directly, pre-populates the editor.
- localStorage or IndexedDB persistence (v2): needs a clear/reset
  UX decision before implementing.

## Open Questions

- Should the STANDARD_STATES constant ship as a JSON config file
  in v1 so users can override it without forking? Decision deferred
  until we know whether real teams hit the taxonomy mismatch.
- Token hasDrift flag: in v1 the user sets it manually. Is that
  actually useful, or does it require an automatic source of truth
  to be worth including at all? Leave it for now; remove in v2 if
  no one uses it.
What the AI now knows

When you run /opsx:continue for tasks.md in the next lesson, your AI has read: the stack context from config.yaml, the problem from proposal.md, the exact scenarios from three spec files, and now the precise function names, signatures, and file locations from design.md. It knows detectMissingStates lives in src/lib/gap-detection.ts. It knows specToMarkdown is a pure function that takes a SpecObject and returns a string. It knows no Zustand, no template engine, no localStorage.

The task list it generates in lesson 7 will be atomic, accurate, and scoped to what you actually decided to build. That's not magic — it's everything you wrote in lessons 4, 5, and 6 doing its job.

If the AI draft has no rejected alternatives

It almost certainly won't have them for every decision. This is not a failure of the AI — it doesn't know what alternatives you considered. It describes what it chose because that's what it can infer from the specs. The rejected alternatives have to come from you. Go through every decision entry and add one line: "Rejected: [alternative] — [specific reason it lost at this scope]." That line is where future developers learn to maintain your codebase instead of fighting it.

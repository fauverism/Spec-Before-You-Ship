Lesson 08

Fast-Forward

The command you'll use on every real project from here on. You did it the slow way first so you know what good looks like. Now see what the AI produces — and exactly where to verify it.

Lessons 4 through 7 took you through every artifact by hand. You wrote the proposal, the specs, reviewed the design doc, and evaluated the task list. That work had one purpose beyond building Bridgespec: teaching you the rubric. You now know what a weak problem statement looks like, what a scenario without an unhappy path costs you, what a decision entry without a rejected alternative fails to record.

With that rubric in your head, /opsx:ff becomes useful. Without it, /opsx:ff produces plausible-looking artifacts that you accept without knowing what they're missing.

What /opsx:ff Actually Does

Fast-forward runs /opsx:continue four times in sequence — proposal, specs, design, tasks — without stopping for human review between each one. The AI reads your openspec/config.yaml context and any description you provide, then generates all four artifacts in a single pass.

Try it on a new throwaway change so you can see the output clearly without touching your Bridgespec work:

you
/opsx:new add-dark-mode
/opsx:ff
ai
Reading change: add-dark-mode
Generating all planning artifacts...

✓ proposal.md — problem, scope, definition of done
✓ specs/theme/spec.md — 3 requirements, 6 scenarios
✓ design.md — context, decisions, trade-offs
✓ tasks.md — 11 tasks across 3 groups

All planning artifacts complete.
Run /opsx:apply to begin implementation.

Open each file and read it against the rubrics from lessons 4–7. You'll find the ff output is genuinely good — better than most unguided prompting produces. You'll also find the gaps that are consistent and predictable.

What ff Gets Right and What It Misses

Artifact
ff gets right
ff commonly misses
proposal.md
Problem statement, scope, a definition of done
Out-of-scope items are thin or missing. The AI doesn't know what you considered and rejected.
specs/
Happy path scenarios, correct SHALL/MUST syntax, valid structure
Unhappy paths and edge cases are underspecified. The AI writes the world where things work.
design.md
Architecture choices, component boundaries, function signatures
Decision entries lack rejected alternatives. The deferred section is empty or absent.
tasks.md
Correct syntax, file references, reasonable grouping and order
Usually solid. Task quality scales with design.md quality.

The pattern: the AI is excellent at describing the happy path and the chosen approach. It's weak at recording what it ruled out. That's not a flaw — it literally doesn't know what you considered and rejected unless you tell it. The fix is always the same: read the output, add the missing unhappy paths to specs, add the missing rejected alternatives to design decisions, populate the deferred section.

A reviewed ff draft takes fifteen minutes. An unreviewed ff draft is just a faster way to write artifacts that miss the same things unguided prompting misses.

The Review Checklist

After every /opsx:ff run, open the four files and check these four things before running /opsx:apply:

ff review checklist 
- [ ] proposal.md: does the out-of-scope list have
       at least three explicit items? If not, add them.

- [ ] specs/: does each requirement have at least one
       unhappy path or edge case scenario? If not,
       add one per requirement before moving on.

- [ ] design.md: does every decision entry name the
       alternative that was rejected and why?
       Fill in any that only describe the chosen approach.

- [ ] design.md: is the Deferred section populated?
       Add anything you considered and explicitly left for later.

That's it. Four checks. If all four pass, the artifacts are ready for /opsx:apply. If any fail, fix them in the file and save — no need to re-run /opsx:ff.

When to Use Which Approach

Write manually
First time through a new feature domain — you need to think, not just review
The problem is genuinely ambiguous and writing it out is how you clarify it
Teaching someone else the SDD workflow for the first time
Any change where the proposal's out-of-scope list is the hardest part to write
Use /opsx:ff
Feature domain is familiar — you know what you're building and what to exclude
Similar change to one you've done before — the AI can reuse context from the archive
Small, well-scoped change — the artifacts are thin and the review takes five minutes
You're on a deadline — ff plus the four-item review is faster than a vague chat

The rule is simpler than the table makes it look: use ff when you could write the artifacts yourself, and choose not to because it would be slower. Use the manual approach when you need the act of writing to figure out what you actually think.

Why this lesson exists

The README for OpenSpec leads with /opsx:ff. Most tutorials about spec-driven development lead with the fast path. This one doesn't — because fast-forward output without the rubric produces artifacts that look complete and aren't. You now have the rubric. The command is fast; the review is where the value is.

Delete the add-dark-mode change when you're done looking at it. It served its purpose.

$ rm -rf openspec/changes/add-dark-mode

End of lesson 8
  • You've seen what /opsx:ff produces and where it's consistent strong and where it reliably falls short
  • You have a four-item review checklist that takes fifteen minutes and catches the gaps
  • You know the decision rule: ff when you could write it yourself and choose not to, manual when writing is how you think
  • The throwaway change is gone — bridgespec-scaffold is the only active change

Lesson 07

Tasks

The last artifact before implementation. A task is not an intention — it names a file, describes an action, and produces something the AI can mark done without asking what you meant.

The task list is where the design doc becomes executable. Each entry is a discrete unit of work with a specific output. When your AI implements a task, it should produce exactly what the task describes — no more, no less — check the box, and move to the next one.

Most task lists fail in one of two directions: too coarse, where each task is really three tasks disguised as one, or too fine, where you're essentially writing pseudocode and the AI is just a transcription service. The right granularity is the one where the AI never needs to make a design decision mid-task, because all the design decisions are already in design.md.

The Format

OpenSpec's progress tracker reads exactly two patterns. Everything else is ignored.

tasks.md — syntax markdown 
- [ ] 1.1 incomplete task — not yet done
- [x] 1.2 complete task — AI has implemented this

# Section headers are ignored by the parser but help humans read
# Regular text lines without checkboxes are also ignored
# Case-insensitive: [X] is the same as [x]

Hierarchical numbering — 1.1, 1.2, 2.1 — is convention, not syntax. The parser counts checkboxes, not numbers. But the numbers matter for two human reasons: they let you reference a specific task in conversation ("the AI skipped 2.3"), and they group related work so you can see which section is lagging when you check progress mid-implementation.

The Task Test

Before committing a task to the list, apply this test: could the AI implement this task without opening any file other than the ones it names? If the answer requires reading another task to understand what this one means, the task is under-specified. If the answer requires making an architectural decision, the design doc is incomplete.

too coarse

One task doing the work of three. The AI will make the sub-decisions itself — and make them differently on every run. You won't know which decision caused a bug.

- [ ] 1.1 Implement gap detection
right

Names the file, names the function or export, scopes the work to one verifiable output. The AI knows exactly what done looks like.

- [ ] 1.1 Write detectMissingStates() in src/lib/gap-detection.ts covering all five category types, with tests in src/lib/gap-detection.test.ts
too fine

You're writing the implementation, not the task. This level of detail belongs in a code comment, not a task list. The AI doesn't need to be told to import a type.

- [ ] 1.1 Import ComponentCategory from src/types/spec.ts
- [ ] 1.2 Declare STANDARD_STATES as a const record
- [ ] 1.3 Add 'interactive' key with seven state names

The config rule you wrote in lesson 2 captures this exactly: "Each task must name the file it produces or modifies." If a task doesn't satisfy that rule, it's almost always either too coarse or describing something that belongs in code, not a task list.

Let the AI Draft It

Clear your context window. Then run:

you
/opsx:continue
ai
Reading change: bridgespec-scaffold
Next artifact: tasks.md (design.md complete ✓)

Drafting tasks.md from proposal, specs, and design...

[writes tasks.md to openspec/changes/bridgespec-scaffold/tasks.md]

✓ tasks.md created. All planning artifacts complete.
Run /opsx:apply to begin implementation.

Open the file. Run the task test on every entry. Two failure modes to look for specifically:

Tasks that don't name a file. "Set up the project structure" is not a task. "Create src/lib/gap-detection.ts and src/lib/export.ts as empty module stubs" is a task. The file name is the atomic unit — if a task can't point to a file, it's either setup work that belongs in the scaffold task or it's an architectural decision that belongs in design.md.

Tasks in the wrong order. The AI generally respects dependencies but occasionally inverts them — writing a component before the reducer it depends on, or writing tests before the function they test. Read the list top to bottom and check that each task can be implemented with only what the previous tasks have produced.

The Bridgespec Task List

Use this as the reference for evaluating and correcting the AI draft. Every task names at least one file. Time estimates are included per the config rule — they matter less for accuracy than for flagging outliers: any task estimated over 90 minutes is probably two tasks.

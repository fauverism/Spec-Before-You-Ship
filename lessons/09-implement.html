Lesson 09

Implement

Run /opsx:apply, watch Bridgespec get built task by task, and learn the one move to make when the AI goes off-script — stop, fix the artifact, resume.

Everything from lessons 1 through 8 has been preparation. The proposal, the specs, the design doc, the task list — all of it exists so that this lesson is not a debugging session. When the AI reads fifteen tasks backed by three spec files and a design doc, it has enough context to implement without guessing. That's the trade you made.

This lesson covers the pre-flight, the run itself, and the most important pattern in the whole tutorial: what to do when the AI produces something that doesn't match a scenario. The answer is not to ask it to try again. The answer is to stop, fix the artifact, and resume. OpenSpec calls this fluid iteration — it's the designed behavior, not a workaround.

Pre-flight

Three things to check before running /opsx:apply. Not suggested — required. Skipping any one of them is the most common reason implementations go sideways mid-run.

pre-flight checklist
[ ]
Clear your context window
Start a fresh chat. Any implementation session that begins in a window already discussing planning, debugging, or other features will carry that context into the AI's decisions. Stale context is the leading cause of the AI "forgetting" what the design doc said.
[ ]
Existing tests pass
Tasks 1.1 and 1.2 are already marked done. Confirm the three tests in spec.test.ts still pass before the AI writes anything adjacent to that file.
npx vitest run src/types/spec.test.ts
[ ]
Tasks 1.1 and 1.2 are marked [x]
The AI reads the task list sequentially and skips completed checkboxes. If 1.1 and 1.2 aren't checked, it will attempt to overwrite spec.ts and spec.test.ts — the files you spent lesson 1 writing carefully.
grep "\[x\]" openspec/changes/bridgespec-scaffold/tasks.md

What Correct Looks Like — Task 1.3

The first real implementation task is gap-detection.ts. This is the right benchmark to check immediately: if the AI produced this file correctly, the rest of the foundation group will follow. Open it and verify three things.

src/lib/gap-detection.ts — expected output typescript 
import { ComponentCategory, SpecState } from '../types/spec';

/**
 * Standard states per component category.
 * Source of truth for gap detection.
 * Matches the taxonomy in specs/gap-detection/spec.md.
 */
export const STANDARD_STATES: Record<ComponentCategory, string[]> = {
  'interactive':   ['default', 'hover', 'focus', 'active', 'loading', 'disabled', 'error'],
  'form-field':    ['empty', 'filled', 'focused', 'error', 'disabled', 'read-only', 'loading'],
  'feedback':      ['info', 'success', 'warning', 'error', 'loading', 'dismissible'],
  'layout':        ['empty', 'loading', 'populated', 'error', 'open', 'closed'],
  'display':       ['default', 'empty', 'loading', 'overflow', 'interactive'],
  'uncategorized': [],
};

/**
 * Returns the names of standard states that are absent
 * from the documented states array for the given category.
 * Pure function — same inputs always produce same outputs.
 */
export function detectMissingStates(
  category: ComponentCategory,
  documentedStates: SpecState[],
): string[] {
  const standard = STANDARD_STATES[category];
  const documented = documentedStates.map(
    s => s.name.toLowerCase().trim()
  );
  return standard.filter(s => !documented.includes(s));
}

Three checks: it imports from ../types/spec, not a redeclared local type. STANDARD_STATES covers all five non-uncategorized categories with the exact state names from your spec. The function lowercases and trims before comparing — matching the case-insensitive scenario you wrote in lesson 5. If all three are correct, run the tests.

$ npx vitest run src/lib/gap-detection.test.ts

 ✓ src/lib/gap-detection.test.ts (4 tests) 6ms
 Test Files  1 passed (1)
 Tests       4 passed (4)

Four tests — one per scenario from specs/gap-detection/spec.md. If any fail, the spec and the implementation disagree. Do not patch the test to make it pass. Read the failure message, find which scenario it covers, and verify whether the spec was correctly interpreted. Either the implementation is wrong (fix the code) or the scenario was ambiguous (fix the spec, then fix the code). Both are valid. Neither is fixed by changing the assertion.

When the AI Deviates

At some point during the implementation run, the AI will produce something that doesn't match a scenario or a design decision. This is not failure — it's information. The question is always: is the spec right and the implementation wrong, or is the spec ambiguous and the implementation is a reasonable interpretation?

A common example: task 3.4 asks for StateList.tsx where isMissing states are "visually distinct." The spec says "amber indicator." The AI might produce a red indicator, or a different icon, or a separate section. None of those match the spec. Here's the move:

1
Stop
Do not ask the AI to "fix it" or "try again" in the same context. Those instructions layer on top of the wrong implementation and produce inconsistent results.
2
Identify which artifact is wrong
If the spec says amber and the AI produced red — the spec is right, the implementation is wrong. If the spec only says "visually distinct" — the spec is ambiguous. Decide which before touching anything.
3
Fix the artifact first
If the implementation is wrong, undo the file change and mark task 3.4 back to [ ] in tasks.md. If the spec was ambiguous, edit the spec to be specific, then mark 3.4 back to [ ]. Either way: the artifact is updated before any code is retried.
4
Resume from the unchecked task
Run /opsx:apply again in the same fresh context. The AI reads the updated spec or task list and implements from where you left off, skipping everything already checked.
✕
Do not: ask it to try again in the same context
The wrong implementation is now in the context window. The retry will be influenced by it.

This is what OpenSpec's documentation calls fluid iteration — "during implementation you can update any planning artifact and continue." The key word is artifact. You update the artifact, not just the prompt. The artifact update is what makes the fix durable across future runs and future changes that touch the same code.

Resume after a break

/opsx:apply is resumable. If you close your editor mid-implementation and come back tomorrow, open a fresh context and run /opsx:apply again. The AI reads the current state of tasks.md, skips every [x], and picks up at the first unchecked task. No ceremony, no re-explaining where you left off.

This works because the task list is the state. Not the chat history, not a session variable — the file on disk. Every checked box is a durable record of what was done.

If a task produces TypeScript errors

The most common cause is a type mismatch between what the AI wrote and the interfaces in spec.ts. Before asking the AI to fix the error, check whether the error is in the new file or in spec.ts. If the new file contradicts a type you defined in lesson 1 — the new file is wrong. Mark the task [ ] again, include the TypeScript error in your context, and re-run /opsx:apply. The AI will read the error as context for the retry.

Lesson 05

Specs & Scenarios

Turn your proposal into testable requirements. The specs/ folder is where the AI learns what it must build, what it must not break, and what the unhappy paths look like.

The proposal told you and your AI what you're building. Specs tell it exactly what correct behavior looks like — for the happy path, for the error cases, and for the edge cases that don't show up in screenshots but absolutely show up in production.

This is the artifact most developers under-write. A spec with only happy-path scenarios is half a spec. The AI will produce a design that handles ideal inputs and silently ignores everything else. This lesson shows you how to avoid that, and gives you three real spec files to write for Bridgespec.

The Format

OpenSpec's parser validates spec files against a specific structure. This is not convention — missing required elements throws a validation error that blocks the artifact graph. Know the rules before you write a line.

## Purpose

Required top-level section. One to three sentences describing what this spec covers. Minimum 50 characters — shorter than that triggers a warning. Write what a reader needs to understand the scope of this spec without reading the requirements.

enforced: missing Purpose → parse error
## Requirements

Required top-level section. Contains one or more level-3 requirement blocks. Must have at least one requirement or validation fails.

enforced: missing Requirements → parse error
### Requirement:
name

Level-3 header. The first line after it must contain SHALL or MUST — this is what the parser looks for to extract the requirement text. Use SHALL for behavior that must always be true. Use MUST for constraints. Pick one and be consistent within a spec.

enforced: no SHALL/MUST → validation error
#### Scenario:
name

Level-4 header nested under a requirement. Each scenario uses bold keywords as step prefixes. Every requirement needs at least one scenario — a requirement with no scenario is a requirement with no way to verify it. GIVEN/WHEN/THEN are convention, not enforced — but use them. They force you to be specific.

convention: GIVEN → state, WHEN → trigger, THEN → outcome, AND → additional

The Scenario Test

Before committing a scenario to the file, apply this test: could you hand this scenario to a developer who has never seen this codebase and have them write a passing test for it? If the answer requires them to ask a clarifying question, the scenario is too vague.

Here's what that looks like in practice — the same behavior specified badly and well:

gap detection — vague scenario fails the test 
#### Scenario: missing states are flagged

- GIVEN a component with some states
- WHEN the user adds states
- THEN missing states should be shown

Three questions a developer must ask before writing a test: which states are "some states"? What does "adds states" mean — one at a time, or after a batch update? What does "shown" look like — a count, a list, a flag on each state object? This scenario tells the AI that gap detection exists. It does not tell the AI what gap detection does.

gap detection — specific scenario passes the test 
#### Scenario: interactive component with documented hover but no error state

- GIVEN a component with category set to 'interactive'
- AND the user has documented a 'hover' state
- AND the user has not documented an 'error' state
- WHEN detectMissingStates() is called
- THEN the returned array includes 'error'
- AND the returned array does not include 'hover'

A developer can write that test right now without asking a single question. The function name is there. The input is specified. The output is precise. This is a scenario.

Happy Path, Unhappy Path, Edge Case

Every meaningful requirement has three types of scenarios. Most specs only write the first one.

happy path unhappy path edge case

The happy path is what happens when everything works. The unhappy path is what happens when input is wrong, a state is invalid, or an operation fails. The edge case is the boundary condition — the empty state, the zero-item list, the maximum-length input, the simultaneous actions.

For Bridgespec, the unhappy paths are the product. A component editor where the user never tries to export an empty spec, never selects the wrong category, never enters a token name without a value — that's not a real tool. Specify the failure modes and the AI will design for them. Skip them and the AI will silently handle them however seems reasonable at implementation time.

The Specs Folder

Inside your change folder, specs/ is a directory of subdirectories — one per feature area. Each subdirectory contains a single spec.md file. For Bridgespec, three feature areas map directly from the proposal:

openspec/changes/bridgespec-scaffold/specs/
├── gap-detection/
│   └── spec.md     ← the core intelligence of the app
├── contract-editor/
│   └── spec.md     ← the form that captures the contract
└── export/
    └── spec.md     ← the thing that makes it all matter

Create those directories now, then write each spec file.

gap-detection/spec.md

This is the most important spec you'll write for Bridgespec. Gap detection is the feature that makes the tool worth using — the moment it flags ⚠ MISSING IN FIGMA on an error state is the moment users understand the product. Specify it precisely.

specs/gap-detection/spec.md 
## Purpose

Defines the behavior of gap detection — the function that compares a
component's documented states against the standard set for its category
and surfaces missing states as flags on the SpecObject. Gap detection
is a pure function: same inputs always produce the same outputs.

## Requirements

### Requirement: standard state detection

detectMissingStates() SHALL return the names of any states in the
standard set for the given category that are absent from the
documented states array.

#### Scenario: interactive component missing error and focus

- GIVEN category is 'interactive'
- AND documented states include 'default', 'hover', 'disabled'
- WHEN detectMissingStates() is called
- THEN the result includes 'focus', 'error', 'loading', 'active'
- AND the result does not include 'default', 'hover', or 'disabled'

#### Scenario: all standard states documented

- GIVEN category is 'interactive'
- AND documented states include all seven standard interactive states
- WHEN detectMissingStates() is called
- THEN the result is an empty array

#### Scenario: uncategorized component

- GIVEN category is 'uncategorized'
- WHEN detectMissingStates() is called with any documented states
- THEN the result is always an empty array
- AND no warning is produced

#### Scenario: state name matching is case-insensitive

- GIVEN a documented state named 'Hover' (capital H)
- WHEN detectMissingStates() is called for an interactive component
- THEN 'hover' is not included in the missing states result
- AND the function does not throw

### Requirement: isMissing flag propagation

The SpecObject states array SHALL reflect gap detection results via the
isMissing flag on each SpecState entry.

#### Scenario: missing state added to array with flag set

- GIVEN gap detection returns ['error'] for the current component
- WHEN the reducer processes the gap detection result
- THEN a SpecState entry for 'error' is added with isMissing: true
- AND the entry is visually distinct in the editor from user-authored states

#### Scenario: user documents a previously-flagged state

- GIVEN the states array contains an 'error' entry with isMissing: true
- WHEN the user adds a description to the error state
- THEN isMissing is set to false on that entry
- AND the entry is no longer visually marked as missing

contract-editor/spec.md

The form that captures the whole contract. The unhappy paths here are where the AI would otherwise guess — what happens if the name field is empty when the user exports? What if a token has a name but no resolved value?

specs/contract-editor/spec.md 
## Purpose

Defines the behavior of the contract editor — the form where a UX
engineer defines a component's name, category, purpose, states,
tokens, and edge cases. All state is managed in the app-level
useReducer. There is no persistence between sessions.

## Requirements

### Requirement: live preview

The spec preview pane SHALL update on every form change without
requiring an explicit action from the user.

#### Scenario: name field update reflects in preview header

- GIVEN the user has typed 'SearchInput' in the name field
- THEN the preview pane shows '# SearchInput.spec.md' as its header
- AND no button press or blur event is required

#### Scenario: empty name field

- GIVEN the name field is empty
- THEN the preview header shows '# Untitled.spec.md'
- AND the export button is disabled
- AND a label beneath the name field reads 'Required to export'

### Requirement: category drives gap detection

Changing the component category SHALL immediately re-run gap detection
against the new standard state set.

#### Scenario: switching from interactive to form-field

- GIVEN category is 'interactive' and 'error' is flagged as missing
- WHEN the user changes category to 'form-field'
- THEN gap detection re-runs against the form-field standard set
- AND the missing states list reflects the new category's gaps
- AND previously user-authored states are preserved unchanged

### Requirement: token validation

A token entry MUST have both a name and a resolved value to appear
in the exported spec without a warning marker.

#### Scenario: token with name but no resolved value

- GIVEN a token row has '--color-brand-primary' in the name field
- AND the resolved value field is empty
- THEN the token row is marked with a yellow warning indicator
- AND the export includes the token row with '(no value)' in the value column
- AND the export does not silently omit the row

#### Scenario: empty token rows are not exported

- GIVEN the user has added a token row but left both fields empty
- WHEN the spec is exported
- THEN that token row does not appear in the output file

export/spec.md

The output of everything. Short spec — export is a pure function from SpecObject to string — but the edge cases around what an incomplete spec produces matter enormously. These scenarios become the tests in lesson 9.

specs/export/spec.md 
## Purpose

Defines the behavior of specToMarkdown() — the pure function that
serializes a SpecObject to a downloadable .spec.md file. The output
must be readable by a developer and a designer without additional
context. Missing or flagged data must appear in the output, not
be silently omitted.

## Requirements

### Requirement: missing states appear with warning marker

The exported file SHALL include all states with isMissing: true,
marked with '⚠ MISSING IN FIGMA' in the status column.

#### Scenario: export with one missing state

- GIVEN the SpecObject has an 'error' state with isMissing: true
- WHEN specToMarkdown() is called
- THEN the states table row for 'error' contains '⚠ MISSING IN FIGMA'
- AND the row is not omitted or moved to a separate section

#### Scenario: export with no missing states

- GIVEN all states have isMissing: false
- WHEN specToMarkdown() is called
- THEN every row in the states table shows '✓ documented'
- AND no warning language appears in the file

### Requirement: export filename

The downloaded file SHALL be named after the component using the
pattern ComponentName.spec.md, with spaces replaced by hyphens.

#### Scenario: component name with spaces

- GIVEN the component name is 'Search Input'
- WHEN the user clicks Export
- THEN the downloaded file is named 'Search-Input.spec.md'

### Requirement: empty spec export

specToMarkdown() SHALL never throw. A spec with missing required
fields produces a valid but incomplete markdown file.

#### Scenario: spec with no states

- GIVEN the SpecObject has a name and purpose but an empty states array
- WHEN specToMarkdown() is called
- THEN the output includes the States section header
- AND the section body reads 'No states documented.'
- AND the function does not throw

Validate Before Moving On

OpenSpec can validate your spec files against the format rules right now, before you commit to the design doc:

$ openspec validate --change bridgespec-scaffold

✓ specs/gap-detection/spec.md        valid
✓ specs/contract-editor/spec.md      valid
✓ specs/export/spec.md               valid

3 specs validated. 0 errors, 0 warnings.

If you see a validation error, it's almost always one of three things: a missing ## Purpose or ## Requirements header, a requirement that doesn't contain SHALL or MUST, or a requirement with no scenarios. Fix it before moving to the design doc — the AI reads these files to generate design.md, and a malformed spec produces a malformed design.

What the AI sees from here

When you run anything in the bridgespec-scaffold change from now on, your AI reads three files before responding: openspec/config.yaml, proposal.md, and all three spec files. By the time it generates design.md in the next lesson, it knows the stack, the problem, the scope, the standard state sets, the validation rules, the function names you've committed to (detectMissingStates, specToMarkdown), and every edge case you've specified.

That's why you write specs before design. The design isn't speculation — it's a response to everything you've already decided.

The spec you skip is the bug you ship

The empty token row scenario in contract-editor/spec.md — the one that says empty rows must not appear in the export — is the kind of scenario that feels obvious while writing it and completely disappears from everyone's mind during implementation. Without it in the spec, the AI will either silently omit the row or include it with blank fields. Both are wrong. Both are in production in tools that skipped this step.

Lesson 01

The Chaos Tax

Why AI coding without specs burns velocity — and what you're actually going to build to fix it.

You've been here. You open a new chat, you describe what you want, the AI writes something. It's close but not quite right, so you clarify. Then clarify again. Then the thing you described in message one is now three layers of misunderstanding deep and the AI is confidently building in the wrong direction.

That's the chaos tax. You're paying it on every feature, every component, every refactor. The currency is time you thought you saved by using the AI in the first place.

the typical loop — without specs
message 1
You:  build me a button component
AI:   [writes a basic button with hover state]

message 2
You:  it needs a loading state
AI:   [adds a spinner, breaks the hover styles]

message 3
You:  the disabled state is wrong, also add error
AI:   [fixes disabled, guesses at error, removes loading]

message 4
You:  why did you remove the loading state
AI:   [apologizes, adds it back, breaks something else]

↑ you are now debugging the AI's memory, not building a product

The problem isn't the AI. The problem is that your requirements lived only in the chat history, and chat history is not a spec. It's noise with a timestamp.

OpenSpec fixes this by giving your requirements a home before the first line of code is written. A folder. A proposal. A list of scenarios. A design doc. A task list. The AI reads those files on every message instead of reconstructing your intent from whatever it remembers.

In this tutorial you're going to build Bridgespec — a web tool for writing component contracts that bridges the gap between design and engineering. States, tokens, edge cases, the why behind decisions. It exports a markdown file that lives in your repo and becomes the shared language between design review and code review.

You'll build it entirely with OpenSpec. Every artifact you write becomes a working demo of the tool. The tutorial and the project are the same document.

What You're Building

Bridgespec is a single-page React app with no backend. Three panes: a form editor on the left where you define a component, a live spec preview in the center, and an export panel on the right. State lives in useReducer at the app root. No auth. No database. The spec file is the persistence layer — it lives in your repo, not a cloud.

Here's what the exported file looks like. This is what you'll be able to produce by lesson 11:

Button.spec.md markdown 
# Button.spec.md
# generated by Bridgespec · 2026-03-27
# openspec: spec-driven-development

## Purpose
Triggers user-initiated actions. Label-first design —
icon alone is insufficient for screen reader and
low-vision contexts.

## States
| State    | Description                          | Status   |
|----------|--------------------------------------|----------|
| default  | Fully interactive, primary variant   | ✓        |
| hover    | 10% darker bg, cursor pointer        | ✓        |
| loading  | Spinner replaces label, non-interactive | ✓     |
| disabled | Opacity 40%, cursor not-allowed      | ✓        |
| error    | Used after failed async action       | ⚠ MISSING IN FIGMA |

## Design Tokens
| Token                     | Resolved Value |
|---------------------------|----------------|
| --color-brand-primary     | #1D4ED8        |
| --color-brand-primary-dark| #1E40AF        |
| --color-text-on-dark      | #FFFFFF        |
| --radius-sm               | 6px            |

## Edge Cases
- Label truncates with ellipsis at 280px container width.
  Do not wrap. Min-width 80px to prevent icon-only collapse.
- Loading state: announce via aria-live="polite" on
  the nearest status container, not on the button itself.

Notice the ⚠ MISSING IN FIGMA flag on the error state. That's the tool doing its job — surfacing the gap before it becomes a bug in production. That flag is the product.

The Data Shape

Before you touch the AI, you write the data model. This is the one file in this project where the spec is the code — the TypeScript interfaces are exactly what the OpenSpec design doc describes.

Create your project directory and this file:

$ mkdir bridgespec && cd bridgespec
$ npm create vite@latest . -- --template react-ts
$ npm install
$ mkdir -p src/types
src/types/spec.ts typescript 
/**
 * Bridgespec — core data model
 *
 * A SpecObject represents a single component contract.
 * It lives in memory per session; the export file is the
 * persistence layer. Flat, serializable, no nesting beyond
 * one level. Mirrors the OpenSpec design doc exactly.
 */

// The component categories we can detect standard states for.
// Each category has a known set of states a component should have.
export type ComponentCategory =
  | 'interactive'   // button, link, toggle, checkbox
  | 'form-field'    // input, select, textarea, datepicker
  | 'feedback'      // alert, toast, banner, tooltip
  | 'layout'        // card, modal, drawer, accordion
  | 'display'       // badge, avatar, tag, progress bar
  | 'uncategorized';

// A single state in a component's state machine.
// isMissing is true when the state was flagged by gap detection
// as a standard state that's not yet documented in Figma.
export interface SpecState {
  id: string;
  name: string;         // 'hover', 'loading', 'error', etc.
  description: string;  // what it looks and feels like
  isMissing: boolean;   // flagged as absent from Figma
}

// A design token assignment for this component.
// hasDrift is true when resolvedValue doesn't match the
// design system's source of truth for that token name.
export interface SpecToken {
  id: string;
  name: string;           // '--color-brand-primary'
  resolvedValue: string;  // '#1D4ED8'
  hasDrift: boolean;     // value doesn't match system token
}

// An edge case is plain English: the condition, the behavior,
// the exact measurement. Not "truncate" — "truncate with ellipsis
// at 280px container width."
export interface SpecEdgeCase {
  id: string;
  description: string;
}

// The complete component contract.
// This is the single source of truth that gets serialized to markdown.
export interface SpecObject {
  id: string;
  name: string;                      // 'Button', 'SearchInput'
  category: ComponentCategory;
  purpose: string;                    // the why, in plain English
  states: SpecState[];
  tokens: SpecToken[];
  edgeCases: SpecEdgeCase[];
  createdAt: string;                  // ISO 8601
  updatedAt: string;
}

// A blank spec — used to initialize the editor.
export function createEmptySpec(): SpecObject {
  const now = new Date().toISOString();
  return {
    id: crypto.randomUUID(),
    name: '',
    category: 'uncategorized',
    purpose: '',
    states: [],
    tokens: [],
    edgeCases: [],
    createdAt: now,
    updatedAt: now,
  };
}
Why write this before anything else

The type file is the spec made executable. When your AI reads SpecObject, it understands the shape of every piece of data in this application. Every component you build next will reference these types. The better this file is, the less you have to explain later. This is the one file worth writing by hand.

Verify the Shape

Create one spec manually and make sure TypeScript is happy. You're not building UI yet — just confirming the model holds.

src/types/spec.test.ts typescript 
import { createEmptySpec } from './spec';
import { describe, it, expect } from 'vitest';

describe('createEmptySpec', () => {
  it('returns a valid SpecObject with empty arrays', () => {
    const spec = createEmptySpec();

    expect(spec.states).toEqual([]);
    expect(spec.tokens).toEqual([]);
    expect(spec.edgeCases).toEqual([]);
    expect(spec.category).toBe('uncategorized');
  });

  it('generates a unique id per call', () => {
    const a = createEmptySpec();
    const b = createEmptySpec();
    expect(a.id).not.toBe(b.id);
  });

  it('sets createdAt and updatedAt to the same timestamp', () => {
    const spec = createEmptySpec();
    expect(spec.createdAt).toBe(spec.updatedAt);
  });
});
$ npm install -D vitest
$ npx vitest run src/types/spec.test.ts

 ✓ src/types/spec.test.ts (3 tests) 4ms
 Test Files  1 passed (1)

Three tests pass. The shape is solid. This is all the code you write in lesson 1.

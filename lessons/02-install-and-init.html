Lesson 02

Install & Init

Get OpenSpec running inside Bridgespec, place the companion, and create your first change folder. By the end your AI can read the spec before it writes a line.

You have a SpecObject and three passing tests. Now you need the workflow layer that turns those types into something an AI can plan against. That's OpenSpec.

This lesson has three parts: install OpenSpec globally, initialize it inside Bridgespec, and place the companion skill where your AI tool will find it. Each part takes two minutes. Together they change how every message in this project works from here forward.

Install OpenSpec

Node.js 20.19.0 or higher required. Check yours first:

$ node --version
v22.14.0

Install globally:

$ npm install -g @fission-ai/openspec@latest
$ openspec --version
1.1.1

Enable the Expanded Workflow

OpenSpec ships with two profiles. The default core profile uses /opsx:propose — one command that generates all artifacts at once. The expanded profile unlocks /opsx:new, /opsx:continue, and /opsx:ff separately, which is what this tutorial uses. You need to turn it on once, globally:

$ openspec config profile
? Select workflow profile › 
  core     (default) propose, explore, apply, archive
❯ expanded           + new, continue, ff, verify, sync, bulk-archive, onboard

Select expanded. This setting is global — it applies to every project on your machine, not just Bridgespec.

Why expanded?

The tutorial writes each artifact by hand at least once before letting the AI generate it. /opsx:new scaffolds the change folder without producing any artifact content — it waits for you. That's the behavior we need in lessons 3–7. /opsx:propose skips ahead and writes everything immediately, which is great in production but defeats the purpose of learning what each artifact does.

Initialize in Bridgespec

Navigate to your project root and run init:

$ cd bridgespec
$ openspec init

The CLI asks two questions. Your answers determine which skill and command files get generated.

Question 2 — schema

Accept the default: spec-driven. This is the schema that generates the four artifacts this tutorial uses — proposal, specs, design, and tasks. Don't customize it yet.

Fill in the Project Context

Open the file OpenSpec just created:

openspec/config.yaml yaml 
# OpenSpec project configuration
schema: spec-driven

# context: background for the AI — not included in artifact output.
# This is the first thing your AI reads before generating any artifact.
# Be specific. Vague context produces vague artifacts.
context: |
  Stack: React 18, TypeScript 5, Vite, Vitest.
  No backend, no auth, no database — static single-page app.
  State lives in useReducer at the app root.
  The core data type is SpecObject — see src/types/spec.ts.
  Output format is a .spec.md file — one per component.
  Testing: Vitest for unit tests (especially pure functions).
  No third-party component library — build from scratch.
  Target user: UX engineers bridging design and engineering.

# rules: per-artifact constraints for the AI.
# These appear as instructions during artifact generation, not in output.
rules:
  proposal:
    - State the problem before the solution
    - Include explicit out-of-scope items
    - Define done in one sentence
  specs:
    - Use Given/When/Then format for every scenario
    - Each scenario must be independently testable
  design:
    - Name every pure function before implementation
    - Explicitly list what is deferred to a later change
  tasks:
    - Each task must name the file it produces or modifies
    - Include a time estimate per task
The context field is doing real work

When your AI runs /opsx:new next lesson, it reads this file first. "No backend, no auth, no database" means it won't propose a Supabase integration. "State lives in useReducer" means it won't suggest Zustand. "See src/types/spec.ts" means it'll reference your actual types instead of inventing its own. Write what you'd say in the first message of a new chat — because this replaces that message, permanently.

Place the Companion

The companion you built in the setup lives at .claude/skills/bridgespec-companion/. If you haven't moved it there yet, do it now:

$ mkdir -p .claude/skills/bridgespec-companion
$ cp -r companion/* .claude/skills/bridgespec-companion/

If you're on Cursor, Windsurf, or Copilot, adjust the path to match your tool's skills directory shown in the init output above. The files inside are identical — only the parent path changes.

Your .claude/skills/ directory now has both OpenSpec's own skills and the companion alongside each other:

.claude/skills/
├── openspec-propose/       ← installed by openspec init
├── openspec-explore/       ← installed by openspec init
├── openspec-apply-change/  ← installed by openspec init
├── openspec-archive-change/← installed by openspec init
└── bridgespec-companion/   ← yours, committed to the repo
    ├── SKILL.md
    ├── references/
    │   ├── spec-types.md
    │   ├── gap-detection.md
    │   └── openspec-commands.md
    └── assets/
        └── button-example.spec.md
OpenSpec's skills are gitignored by default

OpenSpec adds its own skill files to .gitignore because it regenerates them on openspec update. Your companion is different — it's part of the project and should be committed. Make sure .claude/skills/bridgespec-companion/ is not covered by that ignore rule. Check your .gitignore and add an explicit exception if needed: !.claude/skills/bridgespec-companion/

Verify Everything Activates

Open your AI tool and try each of these in a new chat window. You're confirming both OpenSpec and the companion are discoverable:

you: what openspec commands are available?
AI:  I have access to /opsx:new, /opsx:continue, /opsx:ff,
     /opsx:apply, /opsx:verify, /opsx:archive, /opsx:explore.
     What would you like to build?

you: teach me
AI:  Which lesson are you working on, and which AI tool are
     you using — Claude Code, Cursor, Copilot, or Windsurf?

That second response — the session-start question — confirms the companion activated. If you see anything else, the SKILL.md didn't load. Check that the file is in the right skills directory for your tool and that it has valid YAML frontmatter.
